== Purpose and Scope

This document specifies a single, agentic evaluator that assesses capstone submissions across four
domains from the programme:

[cols="1,3,2", options="header"]
|===
| Domain | Capstone(s) covered | Programme week

| A — RAG
| CatalogueIQ (and, by the same pattern, CodeCompass / CourseCompass / ClaimSense)
| Week 3

| B — Agentic AI / Multi-Agent Systems
| SupportPilot (confidence-threshold escalation), CareRoute (hard category-based escalation)
| Week 4

| C — Model Context Protocol
| BankForge (three-server MCP ecosystem for digital banking)
| Week 5

| D — Integrative Capstone
| Nexus (unified financial services concierge combining structured intake, RAG, multi-agent orchestration, and MCP in one deployed system)
| Week 6
|===

Domains A, B, and C are evaluated as independent technology tracks, each with its own three-tier
evaluator (Sections 3–5). **Domain D is architecturally different: it is not a fourth technology to
check, it is a composition layer.** Nexus's own capstone brief states its assessment principle
explicitly — *"integration, not reimplementation"* — and the evaluator is built to match that principle
exactly: Domain D reuses Domains A, B, and C's agents as subroutines, and adds exactly three new agents
whose entire job is to check that the layers genuinely talk to each other in one live request, rather
than sitting disconnected in the same repository (Section 6).

IMPORTANT: SupportPilot, CareRoute, and BankForge do not publish an explicit weighted percentage rubric
in their source specifications — only qualitative deliverables and evaluation criteria. Sections 4.1 and
5.1 propose a weighted rubric for each, derived directly from those stated requirements. **Nexus is
different: it already ships with an official, facilitator-published 8-criterion weighted rubric**
(Section 6.1), so no proposal step is needed for Domain D.

NOTE: *What's new in this edition:* three additions, adapted from a side-by-side comparison with
Tekstac's AI-Role Capability Assessment (a human-candidate evaluation framework that turned out to
share this document's core design philosophy almost exactly). Each is added to the shared architecture
(Section 2) and then instantiated per domain: **(1)** explicit four-band scoring thresholds, so a
numeric score has an agreed meaning; **(2)** a named "reaching" failure signature per domain, giving
facilitators a recognisable pattern to calibrate against, distinct from the hard-escalation rules already
in this document; **(3)** an optional, separately weighted "validated AI tool use" competency, for
programmes where learners themselves use AI coding tools to build their capstones.

== Shared Architecture

=== 2.1 Domain Router

The first agent in the pipeline, ahead of any domain-specific checking, classifies which capstone
domain a submission belongs to.

[cols="2,3", options="header"]
|===
| Agent | Responsibility

| Domain router
| Inspects the submitted repo (README title, directory names, key dependencies) and tags the submission with a `domain` field before dispatch. Signals used: `ragas` + `faiss`/`chromadb` alone → Domain A; `autogen`/`crewai` + escalation logic alone → Domain B; `fastmcp`/`mcp` + a 3-service `docker-compose.yml` alone → Domain C; **all of the above present together, plus a 4+ service `docker-compose.yml` and a single request-handling entry point that calls into intake, retrieval, multi-agent, and MCP code paths in sequence** → Domain D
|===

If the router's confidence is low (a submission mixes signals, or the repo structure is ambiguous), the
submission is escalated to a human facilitator to confirm the domain rather than guessed — the same
"don't silently proceed on an uncertain classification" principle used throughout this document.

=== 2.2 Common Data Model

Every submission, in every domain, is represented with the same JSON shape. Domain-specific agents only
ever add entries to `checks` and populate domain-specific keys inside `rubric_scores` — they never
change the shape itself. For Domain D, `checks` additionally accumulates entries produced by Domain A/B/C
agents running as subroutines, tagged with which layer they inspected.

[source,json]
----
{
  "submission_id": "team-04",
  "domain": "D",
  "capstone_variant": "Nexus",
  "checks": [
    {
      "criterion": "end_to_end_integration",
      "check_name": "intake_output_consumed_by_retrieval",
      "result": "PASS",
      "confidence": "HIGH",
      "evidence": "trace shows classified.product_line='insurance' selected the policy-document retriever, not a fixed default path",
      "source_tier": 2,
      "source_layer": "integration_tracer"
    },
    {
      "criterion": "grounded_reconciled_retrieval",
      "check_name": "structured_and_unstructured_reconciled",
      "result": "PASS",
      "confidence": "HIGH",
      "evidence": "reused from Domain A retrieval/citation checker",
      "source_tier": 2,
      "source_layer": "domain_a_agent"
    }
  ],
  "rubric_scores": {
    "end_to_end_integration": null,
    "structured_intake_quality": null,
    "grounded_reconciled_retrieval": null,
    "multi_agent_orchestration_and_escalation": null,
    "mcp_based_tool_access": null,
    "guardrails_stack": null,
    "deployment_evidence": null,
    "demo_and_debrief": null
  },
  "escalate_to_human": false,
  "escalation_reason": null
}
----

=== 2.3 Common Design Rules

* **Structured hand-offs, not raw transcripts.** Every agent passes a typed JSON object to the next
  agent — never a full conversation dump.
* **Confidence-tagged findings, not silent pass/fail.** Every check is recorded with a confidence level
  (HIGH / MEDIUM / LOW).
* **A fixed, facilitator-owned grading environment.** Every tier that touches a running system evaluates
  against one facilitator-provided dataset and/or test-scenario set per domain.
* **Never let the evaluator silently pass an unverifiable claim as true.**
* **Domain D never re-derives what Domain A/B/C already checked.** If Domain A's retrieval/citation
  checker already confirmed grounded retrieval, Domain D's agents consume that finding rather than
  re-running an equivalent check from scratch — this is what makes Domain D's incremental cost low
  relative to A, B, and C (Section 7.1).

=== 2.4 Observability — The Teenager Framework

Every agent call, in every domain and every tier, is wrapped and logged: which agent ran, what went in,
what came out, tokens spent, and latency. This is required infrastructure for Domain D specifically —
the Integration tracer (Section 6.3) cannot function without a complete, structured trace of every
layer's input and output already being captured.

=== 2.5 Scoring Thresholds — Shared Four-Band Model

Every domain's rubric produces a single weighted percentage score. Without an agreed interpretation of
that number, "72%" means whatever each facilitator privately decides it means. This document adopts one
shared four-band model, applied consistently across all four domains, adapted from the same banding
Tekstac's AI-Role Capability Assessment uses for its own candidate scoring:

[cols="2,1,3", options="header"]
|===
| Band | Score | Interpretation

| Below Threshold
| <50%
| Significant gaps against the rubric; the submission is not ready and needs substantial rework, not minor fixes, before resubmission

| Developing
| 50–64%
| Partial competency demonstrated; targeted rework recommended on the specific flagged criteria before the submission is accepted

| Pass
| 65–79%
| Meets the published expectations for this capstone; ready to proceed to demo and certification

| Distinction
| 80–100%
| Exceeds expectations; strong enough to serve as a reference example for future cohorts and facilitators
|===

NOTE: These cut points are a starting default, not a fixed law — Tekstac's own document states its
thresholds are "tunable per engagement," and the same applies here. What matters more than the exact
numbers is that every domain uses the *same* four bands with the *same* names, so a "Pass" on the RAG
track and a "Pass" on the MCP track carry comparable meaning even though the underlying rubrics differ.

CAUTION: A band is a *starting point for a conversation*, not an automatic decision. A submission at 63%
with one LOW-confidence finding driving most of the gap should be reviewed differently from one at 63%
with several genuinely weak criteria — the confidence tagging from Section 2.3 exists precisely so this
distinction isn't lost inside a single number.

=== 2.6 Failure Signatures — "Reaching" Calibration Notes

A hard-escalation rule (Section 2.3) catches one specific dealbreaker: a single bypass, a single
unauthorised access, and the submission is routed to a human regardless of every other score. That is
necessary but not sufficient — plenty of submissions are weaker than they look without ever tripping a
single hard rule.

For this, each domain also carries a **named failure signature**: a short, recognisable description of
what a submission looks like when it is *not quite ready for that domain's bar, but superficially
resembles one that is* — plausible on the surface, missing the substance underneath. This is a direct
adaptation of the "reaching up" calibration notes in Tekstac's assessment, which serve the same purpose
for human graders assessing candidates one tier above their actual level.

The value of a named signature is consistency: a facilitator who has read a domain's signature once will
recognise the same pattern across many submissions, rather than each facilitator forming their own
private, inconsistent sense of "not quite there." Each domain's specific signature is given in its own
section (3.11, 4.9, 5.9, 6.10) rather than here, since the pattern is different for every domain — a RAG
submission and an MCP submission fail to be "ready" in unrelated ways.

NOTE: A failure signature is descriptive, not a scoring rule. It does not itself dock points; it exists
to help a human interpret a borderline score (Section 2.5) quickly and consistently, in the same way
Tekstac's calibration notes are described as "calibration anchors when norming across evaluators," not as
line items on the rubric.

=== 2.7 AI Tool Usage — An Optional, Separately Weighted Competency

Where learners build their capstones using approved AI coding tools (for example, Claude Code or GitHub
Copilot), this document adds one further, optional competency, adapted directly from Tekstac's own AI
tool usage policy:

* A learner who does not use the available AI tools loses marks **only** on this one criterion — every
  other competency is scored purely on deliverable quality, exactly as in Tekstac's model.
* A learner who uses AI tools and **validates** the output (iterates, tests, catches what the tool got
  wrong) scores well on this criterion.
* A learner who uses AI tools and **bulk-accepts** output without evident validation scores *lower* on
  this criterion than a learner who did not use AI tools at all — unvalidated AI use is treated as a
  worse signal than no AI use, not a neutral one.

[cols="2,3", options="header"]
|===
| Agent | Responsibility

| AI tool usage auditor
| A new shared agent (alongside the Domain router). Inspects whatever usage evidence is available — git commit granularity and messages, an IDE session log, or a learner-submitted usage log — for signs of iterative refinement versus large, unmodified blocks of AI-generated code accepted in a single pass. Produces a confidence-tagged finding, exactly like every other check in this document, rather than a bare score
|===

CAUTION: **This criterion has a real prerequisite Tekstac's environment satisfies and this document's
base programme does not yet describe: a mechanism for capturing AI-tool-usage evidence in the first
place.** Tekstac's assessment VM traces tool usage at the platform level. Nothing in the base capstone
programme (Weeks 2–6) currently instruments an equivalent capture mechanism. Before this competency can
be scored with any real confidence, facilitators need to choose and put in place one of: platform-level
usage tracing (if the learner environment supports it), a required learner-submitted usage log, or
commit-history analysis as a lower-fidelity proxy. Absent any of these, the AI tool usage auditor should
report **N/A**, not a guessed zero — a missing measurement is a different finding from a bad one, and
the confidence-tagging discipline in Section 2.3 exists precisely to keep that distinction visible.

Because this is a *new* competency rather than a restatement of an existing one, adding it to a domain's
rubric changes how that rubric's weights sum to 100%. Sections 4.1 and 5.1 (Domain B and C, already
marked as proposed rubrics — Appendix C) show it folded directly in, with the remaining criteria
rescaled proportionally. Sections 3.1 and 6.1 (Domain A and D, officially published rubrics) instead
report it as a **supplementary score alongside** the published weighting, since altering an officially
published rubric's percentages is a facilitator decision, not an engineering one.

== Domain A — RAG Capstones (CatalogueIQ)

=== 3.1 What This Domain's Evaluator Verifies, By Tier

CatalogueIQ's published rubric weights six criteria: Working system (25%), Chunking and ingestion
quality (15%), Retrieval design (20%), RAGAS evaluation (20%), Evaluation report depth and honesty (10%),
and Demo and panel Q&A (10%).

[cols="3,1,3,3,3", options="header"]
|===
| Criterion | Weight | Tier 1 confidence | Tier 2 confidence | Tier 3 confidence

| Working system
| 25%
| None — cannot confirm the system runs
| High — actually executed
| High (unchanged)

| Chunking and ingestion quality
| 15%
| Medium — code structure only
| High — actual chunk quality observed
| High (unchanged)

| Retrieval design
| 20%
| Medium — code presence only
| High — effect observed directly
| High (unchanged)

| RAGAS evaluation
| 20%
| Low — harness presence only
| High — independently recomputed
| High (unchanged)

| Evaluation report depth and honesty
| 10%
| High — a document-review task
| High (unchanged)
| High (unchanged)

| Demo and panel Q&A
| 10%
| None
| None
| Medium — automated proxy, not a substitute for human judgement (Section 3.9)
|===

NOTE: *Supplementary, not folded in:* if learners use AI coding tools to build CatalogueIQ, the AI tool
usage auditor (Section 2.7) reports a separate 0–100 score alongside this published six-criterion rubric
— it is not blended into the six weights above, since those percentages are officially published and
not this document's to alter unilaterally.

=== 3.2 Tier 1 — Static Evaluator (Report + Code Review Only)

[cols="2,3,3", options="header"]
|===
| Agent | Responsibility | Input / Output

| Intake agent
| Parses the submitted repository: README, source tree, and the evaluation report (Markdown or PDF)
| Input: repo path. Output: file manifest + extracted report text

| Code static analyzer
| Checks, via AST/regex scanning plus an LLM judgment pass, whether required patterns exist: CSV/Markdown/HTML loaders, two distinct chunking functions, embedding calls, FAISS/Chroma usage, a query-expansion step, citation formatting, conversational memory, a RAGAS harness
| Input: source files. Output: checklist with per-item confidence

| Report reviewer
| Checks the report against the required section table; flags missing or templated sections
| Input: report text. Output: section-completeness findings

| Rubric scorer / aggregator
| Combines the two signal sets into a rubric-weighted score with a confidence flag on every line item
| Input: checklist + findings. Output: `rubric_scores` object (Section 2.2 schema)

| Feedback generator
| Turns the score into a facilitator-readable comment sheet
| Input: scorer output. Output: Markdown feedback report
|===

=== 3.3 Tier 1 Design Notes

* No code execution — therefore **no sandbox, no security isolation, no dependency management** is
  required.
* The code analyzer's most important behaviour is catching **unverifiable claims** — a report can state a
  RAGAS score its code never actually produced. Flag "reported metric with no corresponding executed
  call" as LOW confidence.
* Best framed to facilitators as a **triage pass**, not a final grade.

=== 3.4 Tier 1 Effort Estimate

[cols="3,2", options="header"]
|===
| Task | Effort (1 engineer)

| Repo/report ingestion and parsing
| 1–2 days

| Code static analyzer
| 2–3 days

| Report reviewer agent
| 1–2 days

| *~8–11 engineer-days (roughly 2 weeks)*
|===

CAUTION: Biggest risk at this tier is **false confidence**. Never present a Tier 1 score as final

=== 3.5 Tier 2 — Static Evaluator + Live Execution

[cols="2,3", options="header"]
|===
| Agent | Responsibility

| Sandbox runner
| Spins up an isolated container, installs dependencies, ingests the facilitator-fixed ShopSmart India dataset, starts the system behind a standard interface

| Query tester
| Sends the 20-question test set through the running system; captures answer, citations, and retrieved chunks per query

| Retrieval and citation checker
| Cross-checks each citation against ground truth; flags hallucinated specs

| Comparative-query specialist
| Inspects "best X under ₹Y" queries; counts distinct products retrieved and compared

| RAGAS executor
| Independently runs faithfulness, answer relevancy, and context precision; reconciles against self-reported numbers
|===

=== 3.6 Tier 2 Design Notes

* **Standardise the submission interface before Day 1** — require a function or HTTP endpoint contract.
* **Fixed grading dataset** — re-run against one facilitator-provided corpus, not the pair's own.
* **Sandbox security is a first-class concern** — Docker with no unnecessary egress, resource/time
  limits, fresh container per run.
* **Design for partial failure** — surface static findings even when the sandbox run fails.

| 4–6 days

=== 3.11 Scoring Thresholds and Failure Signature

Scores against the six-criterion rubric (Section 3.1) are interpreted using the shared four-band model
in Section 2.5 (Below Threshold / Developing / Pass / Distinction).

CAUTION: *"RAG reaching" failure signature:* answers single-fact questions correctly, but always
retrieves only the top-scoring chunk even for comparative queries ("best earbuds under ₹2000" returns
one product, not several to compare). The evaluation report describes RAGAS scores in confident detail,
but the code never actually calls the RAGAS library — the harness exists but is never invoked. Chunking
looks reasonable for prose but treats every CSV row as one undifferentiated blob. The demo convincingly
handles the happy path but has never been tested against a product that isn't in the catalogue. None of
these alone fails the rubric outright — together, they are the pattern of a submission that looks
farther along than it is.

=== 6.2 Design Principle — Composition, Not Reimplementation

Nexus's own capstone brief states its assessment principle explicitly: *"the core assessment principle
for Week 6 is integration, not reimplementation."* The evaluator is built to match. Five of the eight
rubric criteria are verified by **running Domain A, B, and C's existing Tier 2 agents against Nexus's
endpoints, unchanged** — no new agent code is needed for them. Only three genuinely new agents are
required, and they exist specifically to check the one thing no single-domain agent can see: whether the
layers actually connect in one live request.

|===

| Multi-agent orchestration and escalation (15%)
| Reused from Domain B's trace verifier; hard-escalation non-bypassability reused from Domain B's rephrasing-bypass prober, retargeted at Nexus's hardship/safeguarding/compliance-override categories

| MCP-based tool access (15%)
| Reused from Domain C's discovery/tool-call tester and scoped-access verifier

| Deployment evidence (5%)

| Guardrails stack (10%)

=== 6.4 Tier 2 — Static + Live Execution

[cols="2,3", options="header"]
|===

| Integration tracer
| **New.** Takes one real cross-product request (e.g. "can I pay my insurance premium from my savings account, and does my policy cover that auto-debit?"), and — using the Teenager Framework trace — confirms the *output of layer N is actually consumed as the input of layer N+1*: did the classified `product_line` genuinely determine which retriever ran, did the retrieved context genuinely reach the drafting agent, did the drafting agent's output genuinely determine the MCP tool call made?   Expect this agent to need the most iteration after seeing real submissions.
* As in Domains B and C, a single successful guardrail or escalation bypass is a **hard-fail**,
  regardless of how well every other criterion scores — consistent with the "hard rule, not a tunable
  threshold" principle used throughout this document.

=== 6.10 Scoring Thresholds and Failure Signature

Scores against the eight-criterion official rubric (Section 6.1) are interpreted using the shared
four-band model in Section 2.5 (Below Threshold / Developing / Pass / Distinction).

CAUTION: *"Nexus reaching" failure signature:* each of the four layers — intake, retrieval, agents, MCP
— works in isolation and has its own passing demo, but the real end-to-end request never actually
threads through all of them: at least one layer's output is hardcoded, ignored, or bypassed downstream.
Guardrails modules exist in the repository but aren't wired into the live request path — they'd pass a
code-presence check while doing nothing at runtime. The team can narrate what each component does in
isolation, but not what happens to one real request as it moves through the whole system. This is
precisely the failure mode Nexus's own capstone brief warns evaluators to trace for directly (Section
6.2) — four excellent, disconnected components rather than one integrated system.

=== 7.2 Recommendation

* Build the **shared infrastructure once**, then add domains in programme order: A (Week 3) → B (Week 4)
  → C (Week 5) → D (Week 6) — the evaluator becomes ready for each week's capstone exactly when your
  cohort needs it, and Domain D's low incremental cost is only realised if A, B, and C already exist.
* Within Domains A, B, and C, **Tier 1 first, always** — cheapest tier, useful triage on its own.
* Domain D cannot be usefully built before Domains A, B, and C reach at least Tier 2 — its core value
  (the Integration tracer) has nothing to compose over otherwise. Do not attempt to shortcut this
  ordering to save time; it will not actually save time, since the reused agents are exactly where
  Domain D's cost savings come from.
* Treat Domain B's rephrasing-bypass prober, Domain C's privilege-escalation prober, and Domain D's
  Integration tracer as the three highest-value Tier 2/3 additions across the whole system — each
  directly implements a hard, explicitly stated evaluation requirement from its capstone's own brief.

== Appendix B — Assumptions Behind the Effort Estimates

* Estimates assume one engineer already fluent in Python, prompt engineering, and basic Docker.
* Estimates assume access to the Anthropic or OpenAI API and standard RAG/agent libraries (LangChain,
  FAISS or Chroma, RAGAS, AutoGen or CrewAI, FastMCP) with no procurement delay.
* Calibration effort assumes 5–10 representative submissions (real or synthetic) are available per
  domain before the evaluator is trusted for live grading.
* Domain B and C effort estimates assume the facilitator team, not the evaluator-building engineer,
  authors or reviews safety-sensitive test scenarios (CareRoute's always-escalate cases; BankForge's
  compliance-check scenarios).
* **Domain D's effort estimates are contingent, not standalone** — every table in Section 6 explicitly
  assumes Domains A, B, and C already exist at the corresponding tier. Building Domain D first, or in
  isolation, would not realise these numbers (Section 6.9, caution note).
* Consolidated effort in Section 7.1 assumes the four domains are built by the same engineer(s) in
  sequence, so shared-infrastructure and reuse learnings carry forward.
* Effort figures are engineering build time only; they exclude facilitator time spent reviewing
  escalated or LOW-confidence findings, which recurs every cohort.

== Appendix C — Why Domain B/C Rubrics Are Marked as Proposals, and Domain D Is Not

CatalogueIQ and Nexus ship with explicit, facilitator-approved percentage weightings in their source
specifications. SupportPilot, CareRoute, and BankForge instead describe evaluation *focus* qualitatively.
Sections 4.1 and 5.1 convert those qualitative statements into weighted rubrics by giving each capstone's
own stated "specific design challenge" the highest weight, distributing the remainder across explicitly
listed deliverables, and keeping the overall shape consistent with CatalogueIQ's and Nexus's published
rubrics. Facilitators should treat Sections 4.1 and 5.1 as a **first draft for sign-off**.

Domain D required no such proposal: Nexus's capstone brief already publishes the exact 8-criterion,
percentage-weighted rubric reproduced in Section 6.1, so the evaluator was built to target it directly.

NOTE: The same distinction governs how the new AI tool usage competency (Section 2.7) was added in this
edition: folded directly into Domain B and C's already-proposed rubrics (Sections 4.1, 5.1), but reported
only as a supplementary score alongside Domain A and D's officially published rubrics (Sections 3.1,
6.1) — this document changes what it proposed itself, and only recommends, rather than assumes, changes
to what facilitators have already published.
